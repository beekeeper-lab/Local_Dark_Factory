FORGE build line · Framework Desktop · Fedora Server · headless, SSH-only

The Dark Factory A lights-out software line on local models: humans and AI refine requirements into beans; the line writes the spec, audits it, builds it task by task, audits the build, documents it, audits the documents, and opens the PR. Frontier models build the line — they never run on it.

You spend your time at the front — turning meeting transcripts and conversations into approved, ordered beans — and at the back, reading two teaching documents per change: the specification (the plan) and the implementation detail (what was done). Everything between is the line: a Qwen developer driven through Pi, a gpt-oss judge from a different model family, and a deterministic controller that owns every decision with consequences.

v5.0 · 2026-09-14 · owner: Gregg Reed · status: candidate for baseline approval · companions: DARK_FACTORY_IMPLEMENTATION_PLAN.md, schemas/*.json · changelog & references in §14

Four standing rules.

1. A model never sets its own authority. The controller computes the binding risk tier and effective write-paths from deterministic policy on the actual diff; the judge may raise a tier, never lower it (§08).

2. The judge reviews immutable candidate commits — at three stages (spec, implementation, pre-PR) — and the exact reviewed SHA is what gets pushed and merged (§06, §09).

3. Merging is a per-repo policy, not a global rule. Solo repos may opt into auto-merge and deploy-to-test with a recorded sign-off; shared repos wait for a human reviewer; Tier 3 is never autonomous anywhere (§08).

4. Frontier models are outside the line. Opus builds, tunes, and later monitors the orchestration through PRs to this repository. No frontier provider exists in the runtime configuration (§01, §12).

01 — ROLES & AUTHORITY

Models propose; policy classifies; the controller decides — over real commits

Five roles touch a change. Two are models on Forge, one is deterministic code, one is you, and one is a frontier model that works on the line rather than in it. The developer can edit anything in its tree and the judge can misread a task, so neither holds authority over its own blast radius, and neither is ever reviewed in a form that can still change afterward.

developer

Qwen3.8-27B Q8 via Pi (--mode rpc) in a locked sandbox — no git binary, no credentials, no network by default. Writes the spec and task list, implements one task at a time, writes the implementation-detail content. Proposes; never commits.

judge

gpt-oss-120B, Harmony-verified, deliberately a different model family so its blind spots don't match the developer's. Audits three immutable candidate commits per bean: spec, implementation, pre-PR. Advisory on tier and human review — can raise, never lower.

controller

Deterministic Python under hardened systemd. Owns leases, worktrees, containment, tier computation, gates, every commit, every push, every merge decision, model load/unload, provenance, and the kill switch. The only component with git and credentials.

human (Gregg)

Refines transcripts into beans with the AI and approves them (§04). Reads the spec and implementation-detail documents. Merges PRs in human_required repos; signs the opt-in for auto repos. Owns the kill switch and every Tier 3 change.

outside builder (Opus / Claude Code)

Builds the controller, prompts, templates and schemas; drives the judge and developer through Pi by hand to prove each stage; later monitors telemetry and proposes adjustments — always as PRs to this repository, which are Tier 3 and human-merged. Structurally absent at runtime: the controller's provider registry contains only ollama, and the factory user holds no frontier API key.

Why the strongest model stays outside

The end goal is an application built 100% by local models. If Opus judged or wrote code in the loop, the line would quietly depend on it, and "local" would be a label rather than a fact. Keeping the frontier model at the meta level — improving prompts, decomposition rules, gate manifests and the controller itself — means every improvement lands as reviewable code, and the runtime can be audited by reading one config file.

02 — HARDWARE TRUTH

Forge: one 126 GB pool shared by CPU and GPU — measure whether both models fit

Forge is a Framework Desktop running Fedora Server: an AMD Ryzen AI Max+ class APU with 128 GB of unified memory (~126 GB usable) shared between CPU and GPU. Unlike a discrete card, the GPU's share is a configurable split (BIOS UMA size, or the amdgpu GTT limits on Linux) — so "does it fit in VRAM" is a question about the split you choose, and the answer must come from Phase 0, not from a spec sheet. Both models are already pulled and have both been run on the machine; what has not been measured is whether they are co-resident at useful context.

~63 EST
GB · gpt-oss-120B (MXFP4, MoE)

Fast per token despite its size — a few billion active parameters per token. Judge role.

~30 EST
GB · Qwen3.8-27B Q8

Q8, not Q4 — the ~18 GB figure was the Q4 build. Developer role; needs the larger context.

~93 EST
GB · both, before KV cache

Against ~110 GB GPU share this may co-reside at 16–32K; against 96 GB it likely won't. Phase 0 decides.

Two regimes; the scheduler supports both

Co-resident: both stay loaded; stages run in natural order per bean; swap cost is zero. Serial: one model loaded at a time; the controller batches stages by role across in-flight beans to minimise swaps (§09). Everything downstream — batch sizes, max_inflight, whether the judge is ever loaded mid-bean — is tuned from the swap-time and residency numbers you record here. Until measured, treat every figure above as a hypothesis.

Phase 0 — measure through Ollama, at real context sizes

Ollama's default context is 4096 tokens, so a naïve run measures 4K. Set it explicitly per run. Ollama already runs under systemd on Forge — don't launch a second ollama serve (address already in use); reconfigure the service.

04 — INTAKE

From a meeting transcript to approved, ordered beans — together, then "go"

Intake is the one part of the process that is deliberately not lights-out. It is a conversation between you and the AI that ends with a set of beans you have read, argued about, split, reordered, and approved. Beans do not self-admit: the controller refuses to queue anything whose status is not approved with an approval block naming a human.

  1. Ingest.human → factory intake Drop a transcript (Markdown from the transcription tool), meeting notes, an issue export, or just talk. factory intake --repo owner/name --source transcript.md opens an interactive session against the target repo's read-only tree.
  2. Tear apart.judge model (strongest local reasoner) Extract candidate work items with the source excerpt that produced each; discard chatter; flag ambiguities as questions, not assumptions. Output: a table of work items with proposed grouping.
  3. Draft beans.judge model For each accepted work item: intent, background for a newcomer, read/write paths from the actual repo, acceptance criteria each with a verify, constraints, non-goals, dependencies, a suggested tier, and a size_budget. Schema-validated before it is shown to you.
  4. Review together.human + AI Walk the list. Split beans that would exceed max_tasks; merge trivial ones; reject; reorder; fix dependencies. Every AC must be verifiable by a machine or explicitly marked manual (which forces human review of that bean). This is where most of the human's time and judgement goes.
  5. Approve.human Approved beans get status: approved and an approval block with your name, timestamp and run order. The session commits factory/beans/*.yaml on a factory/intake-<date> branch and opens a PR — you merge it. Beans are Tier 2 paths: the line may read them, never write them.
  6. Go.controller factory go --repo owner/name queues every approved bean whose dependencies are merged, in order. From here the line runs unattended.

Decomposition is the human's highest-leverage act

A 27B developer does not fail because it can't code; it fails because it is asked to hold too much at once. A bean that decomposes into eight or fewer tasks, each finishable and verifiable in one worker session, will get built. A bean that needs thirty will wander. The size_budget is enforced at the specifying stage: if the developer's own task list exceeds it, the bean is bounced back to intake as split_required rather than forced through.

During build-out, the outside builder runs intake

Until the local intake session is proven, Opus in Claude Code plays the AI side of steps 2–4 against the same schemas. The artifacts are identical, so nothing downstream changes when the local judge takes over.

05 — BEANS & TASKS

A bean is an agentic requirement: every criterion says how a machine proves it

The bean is the human-approved packet. The task list is the developer's decomposition of it, written at the specifying stage and audited by the judge. The bean's risk_tier and allowed_write_paths are proposals the controller intersects with repo policy; the task list's write_paths must be a subset of the result.

# factory/beans/bean-014.yaml — validated against schemas/bean.schema.json
schema_version: bean/2.0.0
id: bean-014
repo: beekeeper-lab/payments-svc
title: Add idempotency keys to the payments POST endpoint
intent: Prevent duplicate charges when a client retries POST /payments.
status: approved
source: { kind: transcript, ref: meetings/2026-09-12-payments-sync.md, date: 2026-09-12,
          excerpt: "we double-charged twice last week when the mobile client retried" }
approval: { approved_by: gregg, approved_at: 2026-09-14T15:10:00Z, order: 3 }
context:
  read_paths: [ src/api/payments.py, src/db/models.py, src/util/idem.py ]
  background: >
    Clients retry failed HTTP calls. Without a key the server can't tell a retry
    from a new request. An Idempotency-Key header lets it return the first result.
allowed_write_paths:                   # PROPOSAL — controller intersects with repo policy
  - src/api/payments.py
  - src/db/migrations/**
  - tests/api/test_payments.py         # DoD requires tests → tests must be writable
acceptance_criteria:
  - id: ac1
    text: Repeated Idempotency-Key → one row; both responses match.
    verify: { kind: test, test_id: "tests/api/test_payments.py::test_idempotent_retry" }
  - id: ac2
    text: Keys expire after 24h.
    verify: { kind: test, test_id: "tests/api/test_payments.py::test_key_expiry" }
  - id: ac3
    text: Migration is reversible.
    verify: { kind: command, run: ["alembic", "downgrade", "-1"] }
constraints: [ no new dependencies, p95 latency unchanged ]
suggested_risk_tier: 2                 # advisory; controller computes the binding tier
size_budget: { max_tasks: 6, max_files: 5, max_diff_lines: 400 }
definition_of_done: [ all AC verify pass, gates green, spec and impl-detail docs accepted ]
non_goals: [ do not touch the refunds path, no client SDK changes ]
dependencies: [ bean-009 ]
invariants_ref: factory/invariants/payments.yaml   # independently reviewed source

The task list — the unit of the build loop

  - id: task-2
    title: Look up / store the key in POST /payments
    depends_on: [ task-1 ]
    write_paths: [ src/api/payments.py ]
    satisfies: [ ac1 ]
    verify: [ { kind: test, test_id: "tests/api/test_payments.py::test_idempotent_retry" } ]
  - id: task-3
    title: Expire keys after 24h
    depends_on: [ task-2 ]
    write_paths: [ src/api/payments.py, tests/api/test_payments.py ]

Independent validation means human or a different model family

Some acceptance fixtures come from an independently reviewed source (invariants_ref) outside the developer's reach. For important invariants, independence means a human or a genuinely different model family — a second, differently-prompted Qwen is not independent. The judge's family difference is what makes its audits worth something.

06 — THE LINE

Seven stages, three audits, two documents — every hand-off is a commit

This is your development process, made mechanical: requirement → spec → audit → implement → audit → implementation detail → pre-PR audit → PR. Each audit reviews an immutable candidate commit on the bean's branch; a revise verdict produces a new candidate, never an edit to the reviewed one.

  1. Lease & worktree.controller Atomically lease the next ready bean whose dependencies are merged. git worktree add worktrees/<bean-id> -b bean/<id> from up-to-date default branch. Sync an editable copy (without .git) into the sandbox mount.
  2. Specify.developer via Pi Given the bean, its context paths, and the document standard (§07), write factory/specs/<id>/spec.md (structured Markdown with required sections) and tasks.yaml. Controller validates both against schema and section lint, renders spec.html, checks size_budget (over → split_required, back to intake).
  3. Spec candidate.controller Commit spec + tasks + rendered HTML as an immutable candidate on the branch. Record base_sha, candidate_sha, artifact hashes.
  4. Spec audit.judge Verdict stage: spec_audit. Checks: every AC claimed by ≥1 task; tasks within effective paths and each finishable in one session; risk and blast radius honestly stated; code blocks teach; no assumed stack knowledge; nothing in the spec widens scope beyond the bean. revise → step 2 with feedback_to_worker, revision++. Cap → blocked.
  5. Build — the task loop.developer via Pi · controller drives For each task in dependency order: start a worker session with the spec, the task, and any prior feedback; the worker edits and declares done; the controller syncs back, contains (any edit outside the task's write_paths → reject the whole attempt, reset, scoped feedback), then runs the task's verify list inside the gate container. Fail → the exact failure output goes back as the next prompt, attempt++. max_attempts exhausted → bean blocked with evidence. Verified → next task.
  6. Contain, classify, gate.controller in podman Full containment over the whole diff; compute the binding tier (§08); run all gates from gates.lock.yaml, all AC verifys, independent invariants, hidden tests vs baseline, test-integrity checks, secret scan, diff/file-count limits. Failure → targeted tasks re-open (step 5).
  7. Implementation candidate.controller Commit the contained, gated tree as an immutable candidate_sha. Record diff_sha256, gate_run_id.
  8. Implementation audit.judge Verdict stage: impl_audit over base..candidate, the spec, and gate results — not the developer's justification. revise → step 5 with feedback mapped to specific tasks (a revision produces a new candidate). block → quarantine.
  9. Document.developer via Pi Given the actual accepted diff, the spec, the tasks' teaching_notes and gate results, write factory/impl/<id>/impl-detail.md. Controller lints sections, renders impl-detail.html, commits a new candidate (code unchanged; document added).
  10. Pre-PR audit.judge Verdict stage: pre_pr_audit: does the document describe what the diff actually does (matches_diff), are risk and blast radius stated, do code blocks teach, final security pass over the complete change, and a draft PR body. revise → step 9 only (the code is already accepted; a doc revision cannot touch code).
  11. Push, CI, PR.controller → GitHub Actions Push the exact candidate_sha; open the PR with links to both HTML documents, all three verdicts, tier, and provenance. Enter the CI protocol (§09). Before any merge: verdict.candidate_sha == pr.head_sha and every required_check green for that SHA.
  12. Merge per repo policy; deploy.human or controller human_required: you merge. auto / auto_when_unlocked: the controller merges Tier ≤2 when allowed (§08), then runs post_merge actions — typically workflow_dispatch of the deploy-to-test workflow — and records deployed_test or deploy_failed.
  13. Quarantine, don't stall.controller On cap, budget, or violation: blocked with reason and full provenance; lease released; worktree preserved as evidence; next bean.

"Does not quit early" is a property of the controller, not the model

The developer cannot end a bean. A worker session that stops emitting edits is re-prompted with the unmet verify output; a session that declares done is checked, not believed. The only exits from the task loop are verified or attempts exhausted with evidence. Self-healing is the same mechanism seen from the model's side: it always gets the real failure, scoped to the task it is on.

An unexpected PR-head change is a violation, not a re-review trigger

If pr.head_sha ever differs from the reviewed candidate_sha and the change did not come from the controller's own rebase path, treat it as a policy violation → blocked + alert. Only the controller's rebase path (§09) may legitimately produce a new candidate, and that path re-gates and re-audits.

07 — THE TWO DOCUMENTS

The spec is the plan; the implementation detail is what was done — both teach

These are the human-consumable outputs of the line and the thing you actually read before approving a plan or accepting a change. They are also how a newcomer learns the codebase, so they never assume the reader knows the stack. The developer writes structured Markdown; the controller renders it into a fixed HTML template (dark, printable, self-contained, no external resources). This split matters: a 27B model writing raw HTML is a lint problem; a 27B model filling required sections is a content problem, which is the one we want.

spec.md — required sections (lint-enforced)

  • What and why — the bean's intent in plain language, plus the background a newcomer needs.
  • Current behaviour — how the relevant code works today, with a short annotated code block from the real repo.
  • Proposed change — per task: what changes, where, and an illustrative code block. Each block labelled with the file path.
  • Risk — what could break, how you'd notice, how you'd back out.
  • Blast radius — files, modules, callers, data and deployments touched; explicitly what is not touched.
  • Verification — the AC table with each verify, and any hidden invariants by name.
  • Open questions — anything the developer had to assume. Non-empty here is a signal for the judge.

impl-detail.md — required sections (lint-enforced)

  • Summary — what was done, in two sentences, matching the diff.
  • Walkthrough by task — for each task: the actual diff hunks that matter, explained line by line as a teaching block, plus the task's teaching_note.
  • Deviations from the spec — anything that differs from the plan and why. "None" must be true.
  • Risk & blast radius, as built — re-stated against the real change; anything wider than the spec is a judge finding.
  • Evidence — gate results, AC verify outcomes, coverage delta, test-integrity counts, provenance (SHAs, digests).
  • How to verify locally — commands a human can run.
  • Rollback — the concrete steps.

The judge's document_quality block in the verdict (§10) answers five yes/no questions about each document — risk called out, blast radius called out, code blocks teach, no assumed stack knowledge, matches diff — and any false is a revise. The PR body links both HTML files at their committed paths, so the reviewer reads exactly what the judge audited (hash-bound in verdict.artifacts).

Templates are agent-control files

factory/templates/spec.html and impl-detail.html live in the target repo and follow the html-artifact-output standard. They are Tier 3 paths: the line renders with them and never edits them; changes arrive as human-merged PRs, typically from the outside builder.

Tier 3 is never autonomous in any mode. In auto repos the escaped-defect log is the only ground truth, so every post-merge issue must be recorded against its bean (§11) — that is the price of skipping the reviewer.

The trust boundary

  • Gate definitions, invariants, templates and prompts live outside the writable tree and run from there.
  • Effective write-paths = bean paths ∩ human-approved repo policy; task paths ⊆ effective paths; protected paths escalate the tier.
  • The developer holds no credentials and has no git binary; the controller stages, commits, signs, pushes, opens and (where allowed) merges the PR.
  • Reject, never silently strip, out-of-scope edits — at task granularity and again over the whole diff.
  • Validate against baseline: hidden tests + independent invariants + integrity checks (deleted tests, new skips, weakened asserts).
  • Repository content, transcripts and model output are untrusted input, delimited as data — they never expand paths or verdict authority.
  • No frontier provider in the runtime registry; the factory user's environment is scrubbed of every API key but Ollama's placeholder.

The sandbox contract

  • Read-only filesystem outside the single editable tree; that tree is the only writable mount.
  • No Docker/Podman socket; no SSH agent forwarding; scrubbed environment; no credentials inside.
  • Dropped Linux capabilities and no-new-privileges; CPU, memory, process, output and wall-time limits per worker session.
  • Network disabled by default; an allow-listed proxy only for tasks that genuinely need package access, and only for the gate container.
  • "No git" is structural: the worker image contains no git executable; the editable tree is a synced copy of the worktree without its .git pointer file; the controller keeps the real worktree outside the boundary and diffs after sync-back.

09 — MECHANICS

Explicit states, worktrees, a role-batched model lifecycle, a CI protocol, and a real stop

The state machine — every hand-off is a candidate commit

ready → leased → specifying → spec_committing → spec_auditing
      → (spec_accepted | revise→specifying | split_required→blocked | blocked)
spec_accepted → building ⟳ [task_started → task_verified | task_failed→retry≤N]
      → containing → gating → committing_candidate → impl_auditing
      → (impl_accepted | revise→building(targeted tasks) | blocked)
impl_accepted → documenting → doc_committing → pre_pr_auditing
      → (accepted | revise→documenting | blocked)
accepted → pushing → pushed → pr_open → ci_pending
      → (ci_failed→revise(building) | ci_timeout→retry≤N→blocked
         | stale→rebase→gating (new candidate → re-audit impl + pre-PR)
         | merge_conflict→blocked | merge_pending)
merge_pending → merging → merged → deploying_test → (deployed_test | deploy_failed)   # auto modes
merge_pending → (human merges) → merged → deploying_test → …                          # human_required
terminal: deployed_test · merged (no post_merge) · deploy_failed · blocked · cancelled
  • Every transition carries an idempotency key (bean_id + stage + candidate_sha, or task_id + attempt inside the loop); startup reconciliation re-derives true state from GitHub (branch, PR, checks, head SHA) and the worktree, then resumes or rolls back.
  • Human merge detection: GitHub webhook flips merge_pending → merged; poll + reconciliation are fallbacks.
  • Rebase (from stale) produces a new candidate_sha → re-gate → re-audit implementation and pre-PR (the spec audit stands); a rebase conflict → merge_conflict → blocked. An out-of-band head change is a violation (§06), not a rebase.

Worktrees — one per in-flight bean

/var/lib/darkfactory/repos/<owner>/<name>/
  main/                       # controller's clone; default branch kept current
  worktrees/bean-014/         # git worktree add … -b bean/bean-014
  worktrees/bean-017/
/var/lib/darkfactory/sandbox/bean-014/tree/   # editable copy synced from the worktree, .git excluded

max_inflight (per repo, default 2) bounds concurrent worktrees. Parallelism buys pipelining — one bean in gates while another is in a worker session — not parallel inference: the inference manager serialises model calls. Blocked beans keep their worktree as evidence until a human clears them.

The model lifecycle — role-batched when serial, natural order when co-resident

Switching models costs time (Phase 0 tells you how much). The natural switch point is between beans, but a single bean alternates developer and judge four times. The scheduler resolves this by batching by role across in-flight beans: with the developer loaded, run every bean that is waiting on a developer stage; when that queue is empty (or a bean has waited past max_wait), switch and drain every judge stage. In the co-resident regime the same scheduler runs with swap_cost = 0 and degenerates to natural order.

# inference-manager contract (controller owns it)
ensure_loaded(role)          # if serial and other role resident: ollama stop <other>; preload; wait ready

  regime: auto               # auto = decide from Phase-0 residency probe at startup; or serial | coresident
  swap_policy:
    prefer: bean_boundary    # switch when the current role's queue drains
    max_wait_minutes: 30     # …or when any bean has waited this long for the other role
    min_batch: 1

Whether the judge is ever loaded mid-bean is an empirical question

The spec audit sits between two developer stages, so strict bean-boundary switching would run spec → (wait) → build across two developer loads anyway. Start with max_wait_minutes: 30, watch swap_overhead_pct and bean cycle time in §11, and let the outside builder tune the policy during Phase 5 — that is exactly the kind of adjustment it exists for.

The emergency stop — three verbs

CommandBehaviourRestart
factory pause (SIGINT)Finish in-flight stages; start no new work.Resume pulls next ready.
factory drain (SIGTERM)Finish the current model call / gate, then stop.Reconcile resumes each leased bean from its persisted state.
factory stop-now (control socket)Terminate worker containers now; preserve evidence.Reconcile rolls each bean back to its last candidate; leases released.

All three are reconciliation-safe mid *_committing / pushing / pr_open / merging / deploying_test via idempotency keys. A deploy already dispatched is never cancelled by the factory; it is recorded and left to the deploy workflow.

11 — TELEMETRY

The metrics that gate the unlocks and steer the outside builder

  • False approval rate (judge accept → human rejection as defect / requirement_miss / security / doc_quality). Clears the §08 threshold before a tier unlocks; drives auto-suspend.
  • Rejection taxonomy: defect · requirement_miss · security · preference · stale_branch · unrelated_ci · doc_quality. Only the first three (and doc_quality for document stages) count as false approvals.
  • Escaped defects: issues found after merge or on the test server — ground truth over everything upstream, and the only truth in auto repos.
  • Task attempts per task, revisions per stage, rework rate: high → under-decomposed beans, a weak prompt, or an undersized developer. This is the primary signal the outside builder tunes against in Phase 5.
  • Spec-audit revise rate vs impl-audit revise rate: catching problems at the spec is cheap; a high impl revise rate with a low spec revise rate means the spec audit is too lenient.
  • Swap overhead %, bean cycle time, and time-waiting-for-other-role: decide the scheduler's swap_policy and whether co-residency is worth lower context.
  • Blocked rate and reasons: operational health; a spike in split_required means intake is producing beans that are too large.

Everything is one JSONL event per transition (§10), loaded into SQLite on Forge. A dashboard is a nice-to-have; the outside builder's weekly read of these seven numbers is the requirement.

12 — ROLLOUT

Seven phases, and the outside builder's three-act arc

The authoritative, resumable ledger is DARK_FACTORY_IMPLEMENTATION_PLAN.md. Every phase closes with the same ritual: all tasks checked → exit criteria machine-verified → audit report generated → findings corrected → audit re-run → phase-complete marker committed. The outside builder's role shifts across the phases: build (0–4), supervise (5), test changes only (6 onward).

PHASE 0

Measure on Forge

Residency and GPU/CPU split at 16K/32K/48K, alone and together; swap time both directions; Harmony conformance; Pi drives both models through Ollama. Exit: the co-resident vs serial decision is recorded with provenance.

PHASE 1

One bean, by hand, through all seven stages

Throwaway repo. The outside builder runs each stage with factory step: developer writes spec + tasks; judge audits; task loop with verify; gates; impl audit; document; pre-PR audit; PR. Both HTML documents rendered and read by a human. Exit: every artifact schema-valid, every hand-off a commit, containment proven.

PHASE 2

Controller drives it; the developer cannot commit

Full loop unattended for one bean; fault injection — restart mid-stage, out-of-path edit at task and bean level, duplicate PR, credential exposure, CI failure, stale branch, wrong model loaded, doc that doesn't match diff (judge must catch). Exit: all injections pass; human merge required.

PHASE 3

Intake refinery

Transcript → work items → draft beans → joint review → approval PR → factory go, with the local judge model as the AI side. Exit: a real transcript produces ≥5 approved beans that pass the size budget at the specifying stage. Can run alongside Phase 2.

PHASE 4

Lights-out to PRs

Queue, leases, worktrees, role-batched scheduler, kill switch, reconciliation, telemetry. Exit: ≥48 unattended hours, ≥25 completed beans producing PRs only, all three stop verbs verified, reconciliation-after-crash pass.

PHASE 5

Supervised operation — the outside builder monitors

Opus reads telemetry, verdicts and human rejections weekly; proposes prompt, template, decomposition-rule, scheduler and policy changes as PRs to this repo (Tier 3, human-merged). Exit: two consecutive review cycles with no unresolved drift, rework rate and false-approval rate under their thresholds, swap policy settled.

PHASE 6

Merge modes & deploy-to-test

Enable auto on a signed solo repo with a post_merge deploy; verify deployed_test/deploy_failed paths and the escaped-defect log. Shared repos stay human_required or earn auto_when_unlocked per tier on evidence. Exit: one repo running lights-out to the test server.

STANDING

Model-change protocol — the only time a frontier model touches the line

To swap the judge or developer: shadow-run the candidate model on the last K beans' recorded stages; compare verdict agreement / task pass rate / doc quality against the incumbent; the frontier model adjudicates disagreements only for the duration of the test. Cut over on evidence; record it in the changelog. The runtime registry still contains only ollama.
