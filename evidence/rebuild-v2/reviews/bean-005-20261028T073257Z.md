## 2. ac1 — contradiction detection, adversarially

Confirmed the happy path first: two *independent* explicit-guest contradictions (`g1`/`g2` and `g3`/`g4`, each with a hard `same_table` + hard `different_table` rule pair) both get reported, not just the first:

```

contradictory_hard_rules ('r2-same', 'r2-diff')

```

Then tried the group-mediated case the bean's own dependency (bean-003) makes a first-class, established pattern: `Rule.__post_init__` explicitly allows binding "to at least two guest ids **or to a group**" (`model.py:113-117`), and bean-003's own `default_wedding_rules()` template builds rules this way routinely — e.g. the `vendors` category is a `DIFFERENT_TABLE` rule with `group_id="vendors"` and no explicit `guests` at all.

`_contradictions` (`preflight.py:43-67`) resolves the shared pair via `_shared_pair`, which reads only `rule.guests` (`preflight.py:70-77`) — it never expands a rule's `group_id` into that group's member ids. So a contradiction expressed through a group is invisible:

```python
event = Event(
    id="eX", name="Contradiction via group",
    guests=[guest("g1"), guest("g2"), guest("g3")],
    tables=[table("t1", 4), table("t2", 4)],
    groups=[Group(id="grpA", name="Couple", member_ids=["g1", "g2"])],
    rules=[
        Rule(id="r-group-together", kind=RuleKind.SAME_TABLE,
             hardness=Hardness.HARD, group_id="grpA"),
        Rule(id="r-apart-explicit", kind=RuleKind.DIFFERENT_TABLE,
             hardness=Hardness.HARD, guests=("g1", "g2")),
    ],
)
run_preflight(event)
# => []   (expected: one contradictory_hard_rules finding naming both rules)
```

This is a structurally identical contradiction to the one ac1 names (a hard same-table rule and a hard different-table rule over the same guest pair) — it is just expressed via a group reference instead of inline guest ids, which is exactly how bean-003's template already writes rules. The event is genuinely infeasible (g1 and g2 can be neither together nor apart), and the whole point of this bean is to catch exactly this *before* the solver runs; here it reports nothing and the event goes straight to the solver, which is the failure mode FR-041 exists to prevent.

## Conclusion

Three of the four structural checks (group-size, total-capacity, missing-target) hold up under boundary and adversarial re-derivation, and the contradiction check correctly reports multiple independent explicit-guest contradictions, not just the first found. But the contradiction check (ac1) only resolves a rule's guest pair from its `guests` tuple and never expands `group_id` into group membership, even though group-scoped hard rules (including `DIFFERENT_TABLE` with `group_id`) are an established, already-shipped pattern in this exact codebase (bean-003's wedding template). A hard same-table rule on a group and a hard different-table rule on an explicit pair drawn from that group's members is a genuine, structurally-detectable contradiction that this bean exists to catch — and it silently passes through as "no findings," sending a provably infeasible event straight to the solver. This is the same class of issue flagged in prior beans: code that looks structurally complete but silently fails on an input shape (group-mediated rules) the named tests never construct.

**Repro**: see section 2 above — `run_preflight` on an event with a group-scoped hard `same_table` rule and an explicit hard `different_table` rule on two of that group's members returns `[]` instead of a `contradictory_hard_rules` finding.

**Recommended fix**: in `_shared_pair` (or before calling it), resolve each rule's effective guest set as `set(rule.guests) | set(groups[rule.group_id].member_ids)` when `rule.group_id` is set, then intersect as today.
