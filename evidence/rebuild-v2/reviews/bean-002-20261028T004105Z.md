## 2. Same-pattern gap hunted in `Group` and `Event` — found, but non-blocking

Adversarially constructed each remaining dataclass with garbage/wrong-type values the same way round 1 did for `Guest`:

- **`Group`**: still has no `__post_init__`. `Group(id="g1", name="G", member_ids=["a", "a"])` constructs with no error, despite the class's own docstring stating "a guest id may not appear twice in the same group" — that invariant is enforced only inside `add_guest`, not on direct construction, and `Group(id="g1", name="G", member_ids="notalist")` also constructs silently (stores a string where a list is expected).
- **`Event`**: `Event(id=123, name=None)` constructs with no error (no id/name type checks — but no AC requires any). More notably, duplicate `Group` ids are never rejected, neither via direct construction (`Event(..., groups=[g1_dup, g2_dup])`) nor via `add_group()` — unlike guests/tables, which `_validate_event_contents` checks symmetrically on both paths.

**Why this doesn't block round 2**: unlike the `Guest.rsvp_status` gap, none of this touches a stated AC. ac4's text is purely positive ("a guest may belong to more than one group") and is satisfied regardless; no AC or constraint requires group-id uniqueness or rejects duplicate members on direct construction. I confirmed the hidden suite (`test_hidden_domain.py`) only checks ac4 structurally (a collection-typed annotation exists) and never constructs a `Group`/`Event` adversarially. There is also no silently-wrong *derived* value here the way `eligible` was wrong — it's an unenforced invariant, not a miscomputation. This is architecturally the same category of gap (validation present in a mutator, absent from the constructor), and worth a follow-up bean-003-adjacent note, but it does not violate anything bean-002 was asked to deliver, so it is advisory, not a merge blocker.
