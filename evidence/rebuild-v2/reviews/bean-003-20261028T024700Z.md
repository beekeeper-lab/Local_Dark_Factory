## 2. ac2/ac3 — soft weight bounds and hard-rule-has-no-weight, adversarially

`Rule.__post_init__` validates weight with `_is_real_int` (`type(value) is int`, explicitly excluding `bool` since `bool` is an `int` subclass) and `_is_positive_number` for distance. Ran these directly against the built package (not just reading the existing tests):

```
weight=True (soft)        -> rejected: "a soft rule requires an integer weight in 1..100, got True"
weight=1.5 (soft)         -> rejected: same message
hardness=HARD, weight=5   -> rejected: "a hard rule carries no weight, got 5"
```

The bool-as-int trap the task flagged (the same class of bug as bean-002's `Guest.rsvp_status`) is correctly closed here — `_is_real_int` is a strict `type(x) is int` check, not `isinstance`, so `True`/`False` are rejected as weights exactly where bean-002 would have let a loose `isinstance` check through.

## 3. ac4 / FR-035 — minimum-distance measure, adversarially

```
distance_m=0     -> rejected (FR-035 message)
distance_m=-5    -> rejected
min_zones=0      -> rejected
min_zones=-2     -> rejected
min_zones=True   -> rejected (same bool trap, closed here too)
distance_m=0.5   -> accepted, .distance_m == 0.5
min_zones=1      -> accepted, .min_zones == 1
neither given    -> rejected
```

`_is_positive_number` requires strictly `> 0`, which is a stricter reading than ac4's literal text ("without a numeric distance or zone count") but matches FR-035's spirit ("far apart" must become a real, usable measurement — zero or negative isn't one); not a defect, a defensible and more conservative interpretation.

One real but non-blocking gap found while probing this code path: `min_distance` is the only rule kind whose `__post_init__` branch never checks that the rule is bound to anything. Every other kind requires `len(self.guests) >= 2 or self.group_id is not None`; `min_distance` only requires a positive `distance_m` or `min_zones`, so this constructs without error:

```python
Rule(id="x", kind=RuleKind.MIN_DISTANCE, hardness=Hardness.SOFT, weight=5, distance_m=3.0)
# -> Rule(..., guests=(), group_id=None, target=None, distance_m=3.0, ...) — bound to nothing
```

This is a real asymmetry (the non-min-distance branch enforces a binding, the min-distance branch doesn't), but no AC, constraint, or hidden test requires a min_distance rule to name a subject — ac4 only requires the *measure*, which this rule has. The wedding template never produces an unbound instance (`accessible_seating` always carries `group_id` and `target`). Flagged as a follow-up note, not a blocker, same category as bean-002 round 1's `Group`/`Event` construction-time gaps.

## 4. ac1 — round-trip, and the FR-034 type-count question

Ran `test_all_rule_types_roundtrip`'s pattern independently: built one instance of each of the four implemented `RuleKind`s (`same_table`, `different_table`, `min_distance`, `adjacent_seat`), round-tripped each through `json.dumps(to_dict())` → `json.loads` → `from_dict`, and confirmed full field equality, including that a hard rule never gains an accidental default weight on reload:

```python
r = Rule(id="x", kind=RuleKind.DIFFERENT_TABLE, hardness=Hardness.HARD, guests=("a","b"))
r2 = Rule.from_dict(json.loads(json.dumps(r.to_dict())))
r == r2 and r2.weight is None   # True
```

Checked FR-034 in `benchmark/seating-planner/requirements/REQUIREMENTS.md`: it lists nine guest-relationship bullets (same table, adjacent seats, different tables, min distance, near a guest/group, away from a guest/group, within/outside a zone, near/away a focal point, assign/exclude from a specific table), and this bean only built `RuleKind` values for four of them. This looked, at first, like a real ac1 gap. But the hidden suite's own docstring (`hidden-tests/seating-planner-py/bean-003/test_hidden_rules.py`) explicitly addresses this: the bean "does NOT fix the API... nor what FR-034's rule types are called — the requirement is referenced by number and the names are not in the bean," and the bean's own ac1 verify clause pins a test *id* (`test_all_rule_types_roundtrip`), not a required type count or set of names — so whichever kinds the implementer builds, as long as they round-trip, satisfy ac1 as written. This is consistent with the hidden suite's deliberate choice not to assert type-name coverage. Not a blocker, but worth a note for whoever picks up the remaining FR-034 relationship types (likely future beans, since `target`/`min_zones` already exist on `Rule` and could carry "near/away from a focal point" and zone-based rules without a new field).
