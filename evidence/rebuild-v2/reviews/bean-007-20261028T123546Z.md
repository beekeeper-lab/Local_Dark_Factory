## 1. The diff

Two files touched, within the size budget (max 350 diff lines; actual 276):
`src/seating_planner/solver/hard.py` (+97/-4) and `tests/solver/test_objective.py`
(new, 183 lines). No other files changed. `allowed_write_paths` (`src/seating_planner/solver/**`,
`tests/solver/**`) respected.

`hard.py` adds two scoring helpers and an objective assembly loop, inserted after bean-006's hard
same/different-table constraint loop and before `solver.solve(model)`:

- `_soft_same_table_score`: one `z_t` bool per table, each upper-bounded by every participant's
  seat indicator at that table (`z_t <= seat[p][t]`), so `z_t` can only be 1 when *all*
  participants sit at table `t`. `sat <= sum(z_t)`. No constraint ever forces `z_t` or `sat` to 1 —
  only the maximizer wants them at 1, and only when the chart actually permits it.
- `_soft_different_table_score`: one `apart` bool per participant pair, forced to 0 by
  `apart + seat[a][t] + seat[b][t] <= 2` whenever both sit at the same table `t`; never forced to 1.
  `sat <= apart` for every pair — the group indicator is a conjunction over all pairs, not a single
  pair.
- Both helpers return `weight * sat`; `solve_hard` sums these into `objective_terms` and calls
  `model.maximize(sum(objective_terms))` only if any soft rule contributed a term.
- Hard same/different-table constraints are still plain `model.add(...)` constraints, structurally
  separate from the objective — a soft term literally cannot relax a hard constraint, regardless of
  weight, because CP-SAT will not accept a solution that violates a hard `Add` constraint no matter
  what the objective says.
- `solve_hard`'s status handling (lines 240-247: `INFEASIBLE` -> `"infeasible"`, anything else not
  in `{OPTIMAL, FEASIBLE}` -> raise `SolverTimeout`) is byte-for-byte unchanged from bean-006's
  fixed version. `solve_hard(event: Event, config: SolverConfig | None = None) -> SolveResult`
  signature is unchanged (diffed directly against `main`).

## 2. Independent adversarial testing (beyond the hidden suite and the bean's own tests)

Wrote 7 standalone probes against the installed package inside the pinned gate container (not part
of the repo's test suite), specifically targeting the original bean-007 bug class (bean-021's later
fix in the first build: soft different-table rules scored "satisfied" unconditionally, regardless
of the actual chart) and the other risk areas called out for this review:

1. **Soft DIFFERENT_TABLE actually drives separation.** Two guests, two 2-seat tables, one soft
   different-table rule (weight 50) as the only preference in the model. Result: `g1=t2, g2=t1` —
   the solver actually split them to earn the point. This is the literal negative case for the
   original bug (which would have scored "satisfied" even if the chart put them together).
1b. **Soft DIFFERENT_TABLE correctly scores unsatisfied when infeasible to achieve.** Same rule,
   but only one table exists (capacity 2) so the pair has no choice but to sit together. Result:
   `g1=t1, g2=t1` — correctly forced together (no table to split to), confirming the solver isn't
   just always reporting "apart" regardless of the real chart.
2. **Soft SAME_TABLE**, for completeness: solver put `g1`/`g2` together as the only preference in
   the model. Correct.
3. **Equal-weight conflicting rules, tie-break still finds the true optimum.** `g1`/`g2` soft
   same-table (w5) + `g3`/`g4` soft different-table (w5), 3 tables of capacity 2 (so both are
   jointly achievable: `g1,g2` fill one table, `g3`/`g4` take the other two separately). Result
   reached the true combined optimum of 10/10, independently re-scored from the returned chart by a
   scorer I wrote from scratch (not reusing any solver internals). (My first attempt at this probe
   used only 2 tables, which makes 10 capacity-infeasible to achieve simultaneously — that was my
   test's mistake, not a solver bug; caught and fixed before concluding anything.)
4. **3-member group SAME_TABLE, no partial credit.** `g1,g2,g3` soft same-table (w20), only
   capacity-2 tables available so all three can never share one table. Independently-recomputed
   score: 0, not partial credit for 2 of 3. Same risk class as bean-005's/bean-006's group-handling
   bugs — correctly handled here (`sat <= sum(z_t)` where each `z_t` requires *all* participants,
   not `sat <= z_t` per participant).
4b. **3-member group DIFFERENT_TABLE, all pairs required.** `g1,g2,g3` soft different-table (w20),
   3 tables of capacity 2 (fully achievable). Independently-recomputed score: 20/20, all three at
   distinct tables — confirms the conjunction-over-pairs (`sat <= apart` for every pair) correctly
   requires full mutual separation, not just one pair.
5. **Disabled soft rule excluded from the objective.** A weight-100 soft different-table rule with
   `enabled=False` as the only rule in the model. Across 10 different seeds, the solver sometimes
   seats the pair together (`together_seen=True`), which would never happen if the disabled rule
   were still silently feeding the objective — confirms the `not rule.enabled` guard (`hard.py:213`)
   actually works, not just that it's present in the source.
6. **AC2 under maximum stress.** 10 guests, one hard different-table rule on `g1`/`g2`, plus nine
   *separate* weight-100 soft same-table rules all pushing the identical pair together (900 points
   of soft pressure cumulatively available by violating the hard rule). Result: `g1`/`g2` still on
   different tables — the hard constraint held against the largest soft incentive the model
   allows (9 × max weight), not just a single weight-100 rule as the bean's own test checks.
7. **bean-006's `SolverTimeout` still fires correctly with a live objective.** Reused bean-006's
   own round-2 regression shape (60 guests, 20 tables, one 20-member hard different-table group)
   plus a second, disjoint 20-member soft same-table group (weight 50) to force a real objective to
   be built and optimized over. `time_limit_s=5.0` → `feasible`/60 assigned (unaffected by adding
   the objective). `time_limit_s=0.0001` → raises `SolverTimeout` with the same message format as
   bean-006, `CpSolverStatus.UNKNOWN`. The new soft-objective code path does not interfere with or
   silently absorb an unsettled status.

All 7 probes (8 counting 1b/4b) passed against the real tree. No defect found in any of them.

One adjacent observation, not a blocker: when an objective is present, CP-SAT can return
`FEASIBLE` (accepted by `solve_hard`'s `status not in (OPTIMAL, FEASIBLE)` check) for a solution
that is feasible but not proven optimal if the time limit is tight relative to problem size. For a
pure-feasibility problem (bean-006, no objective) `FEASIBLE` and `OPTIMAL` are interchangeable in
practice since there is nothing to optimize; with bean-007's objective added, a `FEASIBLE`-but-not-
`OPTIMAL` result could in principle return a suboptimal soft score under a tight enough time budget
without raising anything. This is inherent to any time-bounded CP/MIP optimizer, not something a
different implementation would avoid, it is not demonstrated here (the default 10s budget and the
bean's own test fixtures are trivially small for CP-SAT), and it is not in the bean's stated ACs
(which govern small hand-checkable scenarios, not large time-constrained ones). Noting it for
whoever eventually builds a large-scale caller with a tight time budget; not a reason to block this
merge.

## Conclusion

The objective is additive and separate from the hard-constraint model: hard rules are still plain
CP-SAT `Add` constraints, soft rules only ever contribute `weight * indicator` terms to a
`maximize()` call, and every indicator's only constraints push it toward 0, never toward 1 — so no
weight, however large or however many soft rules are stacked, can force or even nudge a hard
constraint. Adversarial testing beyond the bean's own suite and the hidden suite confirms: soft
different/same-table rules actually drive the chart (not a cosmetic always-satisfied score, the
original bug class), 3+-member groups require *all* members for credit (no partial credit), a
disabled soft rule has no effect, equal- and unequal-weight conflicts reach genuine optimality
under capacity constraints, a weight-100 (and even 9×weight-100) soft preference never overrides a
hard constraint, `solve_hard`'s signature is byte-identical to bean-006, and bean-006's
`SolverTimeout` behavior survives unchanged with a live objective in the model. Full gate passes
32/32; hidden suite passes 3/3 against the real tree and 0/3 against an empty tree.
