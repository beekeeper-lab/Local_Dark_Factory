# Pre-merge review: bean-015 (PR #15, run bean-015-20261030T045950Z)

Verdict: do-not-merge. One demonstrated defect.

## Defect: an explicitly locked guest is never offered as an unlock alternative
`src/seating_planner/solver/alternatives.py` `_unlock_probe` (~line 160) calls `_resettle(..., unlocked_guest_ids=frozenset({guest_id}))`. `solve_hard` (hard.py:386-408) keeps an explicit `locked_to_table` lock even when the guest is named in `unlocked_guest_ids`; only the implicit baseline pin is released. So the probe for an organizer-locked guest never finds a feasible re-solve and the option is silently dropped. The spec claim that an explicit lock "needs no special-casing" is wrong. FR-070 (unlocking a specific assignment) covers exactly this case.

Demonstration (gate image, --network=none, branch export): g1 at t1, g3 at t2, capacity 2 each, new guest g2 hard-barred from both.
- lock=None: menu add_table, exception r1, exception r3, unlock g1 (1), unlock g3 (1)
- lock=t1 on g1: menu add_table, exception r1, exception r3, unlock g3 (1)  -- no unlock g1, though releasing g1 would seat g2.

Fix: in _unlock_probe re-solve on an event copy with that guest locked_to_table=None as well as named in unlocked_guest_ids; add a test with a locked guest (all six tests use unlocked guests only).
