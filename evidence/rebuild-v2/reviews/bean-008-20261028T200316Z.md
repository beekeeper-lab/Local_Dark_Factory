## 1. The diff

Four files, within the size budget (max 450 diff lines; actual 409):
`src/seating_planner/solver/result.py` (new, 164 lines), `src/seating_planner/solver/hard.py`
(+/-, net smaller — the old inline `SolveResult`/`_participants` moved out), `src/seating_planner/
solver/__init__.py` (re-export surface), `tests/solver/test_result.py` (new, 220 lines). All paths
are within `allowed_write_paths` (`src/seating_planner/solver/**`, `tests/solver/**`).

`result.py` adds:

- `RuleAssessment` (frozen dataclass): `rule_id`, `kind`/`hardness` stored as `.value` strings (not
  enums), `status` (`"satisfied"|"violated"|"unevaluable"`), `weight`, `affected_guest_ids` (a
  tuple, in rule order, deduplicated against eligibility — the exact same `participants_of` helper
  bean-007's `hard.py` used internally for rule binding, now shared).
- `SolveResult` (frozen dataclass): `status`, `assignments`, `assigned_count`, `unassigned_count`,
  `soft_score`, `rule_states`; a `violations` property filtering to `VIOLATED`; `to_dict()` via
  `dataclasses.asdict`.
- `assess_rules(event, assignments)`: one `RuleAssessment` per *enabled* `Rule` (disabled rules and
  non-`Rule` items are skipped entirely — never counted in any bucket). A rule gets a real verdict
  only if its kind is table-level (`SAME_TABLE`/`DIFFERENT_TABLE`) *and* every one of its
  participants is seated in the given `assignments`; otherwise `UNEVALUABLE`. `SAME_TABLE` is
  satisfied iff all participants land on exactly one distinct table; `DIFFERENT_TABLE` is satisfied
  iff every participant's table is distinct (`len(set(seated)) == len(participants)`) — a true
  group-wide check, not a pairwise one re-derived from the solver's internal pairwise encoding.
- `summarize(status, assignments, event)`: builds `rule_states` from `assess_rules`, then derives
  `assigned_count = len(assignments)`, `unassigned_count` from eligible guests absent from
  `assignments`, and `soft_score` by summing `weight` over exactly the assessments that are both
  `Hardness.SOFT` and `SATISFIED` — i.e. every reported number is recomputed from the chart and the
  rule_states list, not tracked separately anywhere.

`hard.py`'s four `SolveResult(...)` return sites (eligible-empty, no-tables, CP-SAT INFEASIBLE,
CP-SAT feasible) are all replaced with `summarize(status, assignments, event)` calls — the
`assignments={}` short-circuits (empty-eligible, no-tables, infeasible) now also carry full,
properly-computed rule reports instead of a bare status. `solve_hard`'s external behavior
(statuses, `SolverTimeout` semantics, hard/soft constraint model) is otherwise untouched; the only
functional change in `hard.py` is renaming `_participants` to the shared `participants_of` and
wiring the four returns through `summarize`.

## 3. The hard-constraint-exception scoping question (operator note)

Checked `src/seating_planner/solver/hard.py` directly, as asked. Two things confirmed:

1. **For the hard-rule kinds the solver actually enforces** (`SAME_TABLE`/`DIFFERENT_TABLE`, via
   `model.add(...)` constraints — see bean-006/007's structural separation from the objective), a
   feasible chart is guaranteed by CP-SAT to satisfy every one of them; `assess_rules` re-derives
   the same verdict from the chart and will never report one as violated. An infeasible result
   carries no chart (`assignments == {}`), and the solver's own guard (line 143-144) returns
   `infeasible` before any model is even built when there are no tables — so there is never a
   partial chart to report an exception against. This part of the reasoning holds.
2. **One gap the operator's note doesn't surface, worth flagging as a spec-interpretation note (not
   a code defect):** hard rules of kind `MIN_DISTANCE` or `ADJACENT_SEAT` are not enforced by
   `solve_hard` at all — the hard-constraint loop (`hard.py:162-176`) filters to
   `(SAME_TABLE, DIFFERENT_TABLE)` only, same as the soft loop, so a hard `MIN_DISTANCE` rule is
   silently never turned into any model constraint, enforced or otherwise. This is pre-existing
   behavior from before bean-008 (not introduced by this diff — confirmed identical filter logic on
   `main`), and it does not create a false-success risk: `assess_rules` independently classifies
   `MIN_DISTANCE`/`ADJACENT_SEAT` as table-unreadable regardless of hardness, so such a rule is
   always reported `unevaluable`, never `satisfied`, honoring Principle 6 even though the solver
   never attempted to honor the rule itself. So: the operator's conclusion ("nothing in this solver
   could produce a non-empty hard-constraint exception list") is correct, and separately, no
   "exception"/"override"/"authorization" concept exists anywhere in `domain` or `rules`
   (`grep -rn "exception\|override\|authoriz" src/` returns nothing), so FR-049's "every authorized
   hard-constraint exception" clause has no mechanism in this codebase to ever populate regardless
   of solver behavior. Correctly out of scope; not a blocker.

## Conclusion

Every reported number (`assigned_count`, `unassigned_count`, `soft_score`) and every rule verdict is
recomputed from the actual chart and the event's rule list inside `summarize`/`assess_rules` — there
is no separately-tracked counter that could drift, confirmed by independently recomputing all three
from a raw chart by hand (probe F) rather than trusting the result's own fields. The "no false
success" trap this bean exists to prevent is handled correctly on both documented failure shapes:
table-unreadable rule kinds (`MIN_DISTANCE`, `ADJACENT_SEAT`) and a fully infeasible event with no
chart at all — in the infeasible case, *every* active rule, hard and soft alike, reports
`unevaluable`, never `satisfied` or `violated` (probe C). Group-scoped rules (3+ explicit guests or
a `group_id`) correctly report every affected guest, not just a pair, and correctly deny partial
credit for a partially-satisfied group (probe A) — the same bug class that bit bean-005/006/007 does
not recur here. The accounting identity (`satisfied + violated + unevaluable == active rule count`)
holds exactly under a mixed, adversarially constructed rule set, with a disabled rule correctly
excluded from every bucket rather than just one (probe D). The result serializes cleanly to and from
JSON with no enum, dataclass, or set leakage into the payload (probe E). The operator's scoping of
"every authorized hard-constraint exception" out of this bean's result is correct, for the stated
reason and because no exception/override mechanism exists in the codebase at all — a related but
narrower pre-existing gap (hard `MIN_DISTANCE`/`ADJACENT_SEAT` rules are never enforced by the
solver) does not introduce a false-success risk because the report correctly tags such rules
`unevaluable`. Full gate passes 36/36; no hidden suite for this bean.
