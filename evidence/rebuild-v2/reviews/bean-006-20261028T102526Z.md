## 5. ac5 — infeasible vs. UNKNOWN: a demonstrated defect

A genuinely infeasible case (3-member hard same-table group, every table capacity 2) correctly returns `status="infeasible", assignments={}`.

But `solve_hard`'s status check (`src/seating_planner/solver/hard.py:134`) is:

```python
if status not in (cp_model.OPTIMAL, cp_model.FEASIBLE):
    return SolveResult(status="infeasible", assignments={})
```

This treats `cp_model.UNKNOWN` — CP-SAT's honest "ran out of time before proving anything" result — identically to `cp_model.INFEASIBLE` — a proven negative. These are not the same claim, and the module's own docstring even frames this as deliberate ("a solver status that is not a proven answer is reported infeasible"). AC5's text is "an unsatisfiable hard-constraint set returns an infeasible result" — it does not say an unproven-but-possibly-satisfiable set should return the same string.

**Repro**, run against the installed package (same construction `solve_hard` itself uses — `event.guests`/`event.tables`/`Group`/`Rule`, no internals touched):

```python
# 60 eligible guests, 20 tables of capacity 3 (exactly 60 seats), one hard
# DIFFERENT_TABLE rule on a 20-member group (forces those 20 across 20 distinct tables).
event = Event(id="e6", guests=[...60 guests...], tables=[...20 tables, cap 3 each...],
              groups=[Group(id="big", member_ids=[f"g{i}" for i in range(20)])],
              rules=[Rule(id="r-big-diff", kind=RuleKind.DIFFERENT_TABLE,
                          hardness=Hardness.HARD, group_id="big")])

solve_hard(event, SolverConfig(time_limit_s=5.0,    seed=1))  # -> status="feasible", 60 assigned
solve_hard(event, SolverConfig(time_limit_s=0.0001, seed=1))  # -> status="infeasible", 0 assigned
```

Both calls solve the *exact same* `Event` object; only `time_limit_s` differs. At a realistic budget the problem is proven feasible (60/60 seated). At a tiny budget — reachable because `time_limit_s` is an explicit, caller-configurable, unvalidated float with no enforced minimum — `solve_hard` reports `"infeasible"`. I confirmed independently, by rebuilding the identical CP-SAT model by hand with `solver.status_name(status)`, that the raw solver status at the tiny time limit is literally `CpSolverStatus.UNKNOWN`, not `INFEASIBLE`:

```
time_limit=0.0001: status=UNKNOWN (CpSolverStatus.UNKNOWN) wall_time=0.0019
```

So the public API's `"infeasible"` string is used for two semantically opposite situations: "proven no solution exists" and "don't know, ran out of time" — indistinguishable to any caller. This is exactly the risk class flagged going in: a solver status that isn't a proven answer gets silently folded into a different, stronger claim. The practical harm: at production scale (`MAX_GUESTS=500`, `MAX_TABLES=60` in `domain.py`) with a realistically dense set of hard group rules, a genuinely satisfiable event could time out under time pressure and be reported to the organizer as impossible — a false negative that could cause a user to needlessly relax or delete a real, satisfiable constraint set, which is the opposite of FR-045's "satisfy every hard constraint unless explicitly authorized." I did not need an implausibly large instance to trigger this in principle — any caller who sets a short time limit against the production-scale ceiling can, since nothing prevents `UNKNOWN` from occurring there just because this particular 60-guest demo instance resolves quickly at 5s.

This is a real, demonstrated gap: not a hypothetical about solver internals, but the literal behavior of the shipped `solve_hard` function reproduced above with an unmodified checkout.

## Conclusion

ac1, ac2, ac3 (including 3+-member group-scoped same/different-table rules — the risk class flagged going in, by analogy to bean-005) and ac4 all hold up under adversarial re-derivation; no off-by-one at the capacity boundary, no stray variable or leaked capacity for ineligible guests, and group-scoped rules are enforced correctly (fully, not just pairwise-on-a-subset) for 3+ members. The defect is in ac5's boundary case: `solve_hard` cannot distinguish CP-SAT's `UNKNOWN` (no proof either way) from `INFEASIBLE` (proven no solution) — both collapse to the same `status="infeasible"` result the caller cannot tell apart from a genuine negative. Demonstrated above against the exact same `Event` object at two different `time_limit_s` values, with the raw CP-SAT status printed to confirm `UNKNOWN` is what actually occurs. None of the five named AC tests exercise this path (they all use generous 5s time limits on tiny instances), so the gate passed clean without ever touching it.

**Recommended fix**: add a third, honest status (e.g. `"unknown"`) distinct from `"infeasible"`, returned when `status == cp_model.UNKNOWN`, so a caller (and FR-050/051's eventual "identify the conflict" / "recommend a corrective action" behavior) can tell "no solution exists" apart from "ran out of time — try a longer limit or a smaller problem."
