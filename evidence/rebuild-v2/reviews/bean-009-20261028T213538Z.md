## 3. Independent adversarial testing (beyond the bean's own tests)

The bean's own fixture (`scenario()`: g1+g2 soft-paired weight 10, g1≠g3 soft
weight 1, two 2-seat tables) does have a real tie — which physical table
(`t1` or `t2`) the pair sits at is free, both scoring 11 — so it is not a
single-optimum fixture. But I went further and tested on genuinely richer
symmetric events, and tested the one case the task specifically flagged: what
happens if a caller sets `num_workers` above 1 through the now-public API.

Ran 7 probes inside the pinned gate container against the installed package:

- **Probe 1 — the bean's own tie fixture, default config (`num_workers=1`),
  same seed, 10 repeats.** Byte-identical every time. ac1 holds on the real
  tie, not just a one-answer fixture.
- **Probe 2 — a fully symmetric 8-guest/4-table event with zero rules** (every
  guest and every table interchangeable — about as many tied optima as this
  model can have), `num_workers=1`, same seed, 2 runs: identical. Confirms ac1
  on a much harder symmetry case than the bean's own fixture.
- **Probe 3 — the task's named risk: `SolverConfig(num_workers=8)` on the same
  fully-symmetric event, same seed, 8 repeats.** All 8 runs returned the
  identical chart in this environment. I want to be precise about what this
  does and doesn't show: CP-SAT's own documented guarantee is that
  determinism-per-seed requires `num_workers=1`; the library gives no
  determinism guarantee above that, and the code does **not** validate or
  reject `num_workers > 1` — a caller can set it, and nothing defends against
  the non-determinism CP-SAT's own docs warn about. In this sandboxed
  container (likely CPU-limited) the race never manifested on this small a
  model, so I cannot *demonstrate* a concrete divergent pair of charts under
  multi-worker — meaning this is not a provable code defect, only a
  theoretical exposure. Critically, this is the exact, named "open owner
  decision" in the bean's own `context.background` ("there is a real tension
  with NFR-001's 15-second target... this bean's job is to make the
  configuration explicit rather than to resolve it") and is explicitly listed
  as a `non_goal` ("no performance tuning against NFR-001 in this bean"). The
  bean's job was to make `num_workers` explicit and recorded, which it does;
  resolving whether callers may ever pick `num_workers > 1` is out of scope by
  the bean's own text. Not a blocker, but worth a caller-facing note: nothing
  stops a future caller from picking `num_workers=4` and silently losing ac1's
  guarantee — the config schema allows it without comment.
- **Probe 4 — ac4 on the bean's own tie fixture, seeds 0 through 19.** All 20
  seeds produced the *identical* assignment. This is the exact trap the task
  named: "a test that can't tell determinism from luck." The bean's own
  `test_seed_change_is_visible` only asserts internal consistency per seed and
  that the stored seed matches — it never asserts the assignment actually
  differs across seeds, so it would pass identically whether or not seed
  genuinely drives the search. That's a legitimately weak test, not a code
  defect: ac4's text says a seed change "may" change the assignment, so a
  fixture where it never does is not itself non-compliant — but it leaves the
  "is seed real or decorative" question unanswered by the bean's own suite.
- **Probe 5 — closing that gap independently: same 8-guest/4-table fully
  symmetric event as probe 2, seeds 0 through 9.** 10 *distinct* assignments
  across 10 seeds. This proves the seed genuinely drives CP-SAT's search and
  the result is not suppressed, normalized, or hidden — ac4's real behavior is
  implemented, just not exercised by the bean's own chosen fixture. Combined
  with probe 4, this also confirms the "no difference" case (single rule
  structure gives the same tie-break regardless of seed) is correctly *not*
  misreported as a failure — both fixtures report their actual, honestly-
  computed `solver_config.seed` either way.
- **Probe 6 — config-recording on the two early-return branches the bean's own
  tests don't reach** (no-eligible-guest and no-tables short-circuits, which
  return before any `CpSolver` is ever constructed). Both correctly stamp the
  exact `cfg` object passed in (`time_limit_s=3.3/seed=99` and
  `time_limit_s=4.4/seed=55` respectively, matched by dataclass equality) —
  ac2 holds on every `summarize()` call site, not only the two the bean's own
  tests exercise (CP-SAT-feasible and CP-SAT-infeasible).
- **Probe 7 — JSON round-trip of a `SolveResult` carrying a nested
  `SolverConfig` dataclass.** `dataclasses.asdict()` recursively flattens the
  nested frozen dataclass into a plain dict (`{"time_limit_s": 5.0, "seed": 1,
  "num_workers": 1}`); `json.dumps` succeeds with no repr leakage.

All 7 probes passed; no divergence between the recorded `solver_config` and
the config actually driving `solver.parameters`, and no sign of output
post-processing standing in for real determinism.

## Conclusion

This bean does exactly what the task predicted it should: it exposes
bean-006's existing `num_workers=1` / `random_seed=cfg.seed` pinning through

with no validation or warning, and CP-SAT gives no determinism guarantee
above 1 worker — is a real, named, in-scope-excluded tension from the bean's
own spec text and non_goals, not a demonstrated code defect; I could not
produce an actual divergent pair of charts under multi-worker in this
container, only confirm the code does not defend against it. Full gate passes
40/40; no hidden suite for this bean.
