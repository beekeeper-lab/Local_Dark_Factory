## ac2/ac3 — a real, demonstrated gap: `Guest` does not validate or coerce `rsvp_status`

The review brief specifically calls out "RSVP status set via a raw string vs the enum" as a case to try. I did, and it breaks two ways:

```python
from seating_planner.domain import Guest, RsvpStatus

# 1. An invalid value is silently ACCEPTED, not rejected, when passed as a plain str:
g_bad = Guest(id="g2", name="Bad", rsvp_status="NotAStatus")
g_bad.rsvp_status   # -> "NotAStatus" (no exception at construction)
g_bad.eligible       # -> False (silently treated like Declined/Cancelled)

# 2. A *valid* value, passed as the equal plain str instead of the enum member,
#    silently produces the WRONG answer instead of either working or raising:
g_str  = Guest(id="g3", name="ValidStr",  rsvp_status="Confirmed")
g_enum = Guest(id="g4", name="ValidEnum", rsvp_status=RsvpStatus.CONFIRMED)
g_str.eligible   # -> False  (wrong: a Confirmed guest must be eligible per ac3)
g_enum.eligible  # -> True   (correct)
```

Root cause: `Guest` has no `__post_init__` at all, so nothing validates or coerces `rsvp_status`. `eligible` tests `self.rsvp_status is RsvpStatus.CONFIRMED` — an identity check, so even a value-equal plain string (`"Confirmed"`) fails it, because `str.__new__("Confirmed")` is never `is` the `RsvpStatus.CONFIRMED` singleton. This is inconsistent with `Table` in the very same file, which does validate and normalize its constructor inputs in `__post_init__` (capacity type/range, position shape/type, coercing ints to floats) — `Guest` is the one dataclass in this bean with no construction-time validation at all, despite ac2's text ("RSVP status accepts exactly ... and rejects anything else") and the bean's stated intent ("the vocabulary of the product exists as validated data structures").

Why the gate missed it: `tests/domain/test_guest.py::test_rsvp_status_values` (ac2's own named test) only exercises `RsvpStatus("Confirmed")` etc. directly — it never constructs a `Guest`. The hidden suite's RSVP test (`test_rsvp_has_exactly_the_four_named_values`) is a static substring scan over the source file, not a behavioral test — confirmed by reading it (see above). Neither test ever constructs `Guest(rsvp_status=<str>)`, so this gap is real and genuinely undetected by the gate, not a false alarm.

mypy does catch the type mismatch *statically* for code that gets type-checked (confirmed: `mypy` on a probe file calling `Guest(..., rsvp_status="Confirmed")` reports `error: Argument "rsvp_status" to "Guest" has incompatible type "str"; expected "RsvpStatus"`) — but that only protects call sites inside this mypy-checked package. Any future caller building a `Guest` from parsed input (CSV/JSON/CLI import — the obvious next step for a guest list, and squarely what "rules and the solver have something concrete to refer to" implies) gets no runtime guard at all, and a typo or unnormalized value is silently misclassified as ineligible rather than rejected.

**Fix is small and consistent with the file's own pattern**: give `Guest` a `__post_init__` that coerces/validates, e.g. `self.rsvp_status = RsvpStatus(self.rsvp_status)` (raises `ValueError` on anything invalid, and normalizes the valid-string case to the real enum member, exactly mirroring what `Table.__post_init__` already does for `position`).

## Why this blocks

The gap is concrete, reproduced twice above (invalid value silently accepted; valid value silently misclassified), sits exactly on ac2/ac3's stated behavior, and is inconsistent with this same file's own validation pattern for `Table`. It is not a style nitpick or a documentation issue — it's a silent-wrong-answer path in the "eligible" rule that bean-003's rule model and the eventual solver are meant to rely on as ground truth. Recommend a follow-up commit adding `Guest.__post_init__` coercion/validation (one line, same idiom as `Table`), plus a behavioral test constructing `Guest` with a raw string, before merge.
