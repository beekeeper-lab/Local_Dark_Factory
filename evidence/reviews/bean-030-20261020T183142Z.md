## A real, demonstrated gap — not blocking

`validate_event`'s solve-only reference loop iterates `entry.guest_ids` and `entry.group_ids` directly (`for guest_id in entry.guest_ids: ...`) without checking they are iterables of strings first. `Rule.guest_ids`/`group_ids` are plain mutable dataclass fields with no type check anywhere (`Rule._check` never validates them, so a type-confused value was never refused at construction either). Reproduced against the PR-head tree:

```python
r = Rule(id="r4", rule_type=RuleType.SAME_TABLE, hardness=Hardness.SOFT, weight=10, guest_ids=("g0", "g1"))
event.add_rule(r)
r.guest_ids = 5          # not iterable
solve_event(event, mode="planning")
# -> TypeError: 'int' object is not iterable
#    at validation.py:101, "for guest_id in entry.guest_ids:"
```

The same mutation reaches `save_event` too, crashing with the identical `TypeError` inside `Rule.to_dict()`'s `list(self.guest_ids)` (store/__init__.py:167), not `EventValidationError`. In both cases the previously saved event is left untouched (the transaction's `with self._conn:` rolls back on the uncaught exception, so ac4's core safety property — a refused save never corrupts what was there — still holds); the failure is only that the raised type is a raw `TypeError`, not the promised `EventValidationError`.

Not blocking, for three reasons: (1) it requires reassigning `guest_ids`/`group_ids` to a non-iterable scalar, not a same-type value changed to an out-of-range one — the only kind of post-construction mutation the bean's background, ac1 and ac2 actually name (soft weight, hard weight, distance measure, guest count, duplicate id, reserved_seat, and *unknown-id* references, never *malformed-type* references); (2) grepped the whole `src/` tree — no production code anywhere reassigns `.guest_ids`, `.group_ids`, or `.weight` after construction (unlike `.status`/`.reserved_seat`, which do have realistic post-construction write paths), so this is not a reachable vector through any existing caller, only a hand-built adversarial mutation; (3) the hidden suite's own 8 scenarios (`test_hidden_validate_on_use.py`, 24 parametrized cases) do not probe this corner either, and both directions pass it (control: `ModuleNotFoundError`/24 failed against an empty tree; real: 24 passed against PR head) — confirming the suite is scoped the same way ac1/ac2's text is. Worth a follow-up bean or amendment if the operator wants `Rule`'s collection-typed fields type-checked on use as well as on construction.
