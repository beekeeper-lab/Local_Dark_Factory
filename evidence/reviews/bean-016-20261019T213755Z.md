## VERDICT: do-not-merge

## Defect (demonstrated)

`optimize()` represents "the solve is infeasible" identically to "the solve succeeded and proposes zero changes," and `accept()` performs no check before writing — so accepting an infeasible optimize's proposal **silently destroys a previously saved, real chart**, replacing it with `{}`.

**Cause** (`src/seating_planner/solver/proposal.py:114-115`, `optimize`):

```python
if result.status != "feasible" or not result.assignments:
    return Proposal(event.id, mode, {}, ())
```

An infeasible `SolveResult` always has `assignments == {}` (`result.py:59`: "Empty exactly when infeasible"). This line maps that case to `Proposal(event_id, mode, {}, ())` — the exact same shape ac3 defines for "a proposal that changes nothing." `Proposal` carries no status/ok field, so nothing distinguishes "solve failed, there is no chart to accept" from "solve succeeded and the saved chart is already correct." `accept()` (line 129-135) does not inspect `changes`, does not compare `assignments` against the store's current chart, and does not refuse an empty `assignments` — it unconditionally calls `store.save_chart(proposal.event_id, proposal.assignments, actor=actor)`, which upserts whatever `assignments` is, even `{}`, over an existing non-empty row.

This is a self-acknowledged open question in the run's own `spec.md` ("Infeasible optimize... I assumed `optimize` returns a `Proposal` with empty `assignments`... No AC covers this case, so this is a declared assumption, not a requirement") — the assumption itself is what's unsafe: nothing in `accept`'s path guards against applying it.

**Repro** (pinned gate image `ghcr.io/beekeeper-lab/factory-gate-python:20260914`, run against the PR branch head via `podman run --rm -v "$PWD":/work:Z -w /work -e PYTHONPATH=/work/src ... python3 repro.py`):

- Event: 1 table, capacity 1; 2 confirmed guests → `solve_event(event, mode="planning").status == "infeasible"` (confirmed directly).
- A real saved chart already exists: `repo.save_chart("e1", {"g1": "t1", "g2": "t1"}, actor="seed")`.
- `proposal = optimize(event, saved={"g1": "t1", "g2": "t1"}, mode="planning")` → `proposal.assignments == {}`, `proposal.changes == ()`.
- `accept(repo, proposal, actor="organizer")` → `repo.load_chart("e1") == {}`.

Output:
```
solve_event status: infeasible
saved chart before optimize/accept: {'g1': 't1', 'g2': 't1'}
proposal.assignments: {}
proposal.changes: ()
saved chart after accept: {}
DEFECT CONFIRMED: accept() overwrote a real saved chart with {} because optimize()
returned an infeasible result disguised as an empty, valid proposal.
```

This directly contradicts the bean's intent ("No recalculation reaches the saved chart without the organizer first seeing every guest whose table would change and accepting it") — here, a *failed* recalculation reaches the saved chart as a full wipe, shown to the organizer as "nothing to review," with an audit entry (`apply_chart`, actor-named) that looks exactly like a deliberate, successful accept.

A plausible real trigger: a table's capacity is reduced (or a guest added) after a chart was accepted, making the event infeasible; the next `optimize()` call quietly produces an empty "no changes" proposal instead of surfacing the infeasibility, and an organizer who accepts it (reasonably, since the UI would show no changes) erases the existing seating chart.

## Minor, non-blocking

- `Repository.save_chart`/`accept` give no technical enforcement that the comparison was ever shown to anyone; any caller holding a `Repository` can write a chart without going through `optimize`/`compare_charts` at all (same latitude `save_event` already has).
- `optimize`'s docstring says "there is no chart to accept" for the infeasible case, which is the correct framing the code does not actually enforce — fixing the code to match this docstring (e.g. raising, or adding a status so `accept` can refuse) would resolve the defect above.
