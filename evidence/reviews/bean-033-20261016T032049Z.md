## Defect 1: the low-disruption shortage short-circuit probes with the limit relaxed, not the real one

`hard.py:726-734` (`_diagnose_low_disruption`'s first check): the shortage-only
short-circuit is supposed to answer "does curing the shortfall alone, with the real
movement limit in force, restore feasibility?" (this run's own `spec.md`, Task 3 section:
*"Short-circuit (real limit, real cap). If the base model `_build_model(…,
current=current, movement_limit=movement_limit, slack_bound=shortfall)` is
satisfiable…"*). The committed code instead passes `movement_limit=None`:

```python
if shortfall > 0 and _probe_status(
    _build_model(
        event, eligible, current=current, movement_limit=None, slack_bound=shortfall,
    )[0],
    _PROBE_SECONDS,
) in (cp_model.OPTIMAL, cp_model.FEASIBLE):
    return InfeasibilityReport((), shortfall, _recommendations_for(event, frozenset(), frozenset(), shortfall))
```

This asks a strictly easier question (capacity cured *and* movement unrestricted) than
the one it is supposed to answer, so it fires whenever relaxing the limit — not just
adding seats — would help, even when the real limit forbids exactly that. The result:
a real rule-vs-movement-limit conflict silently vanishes behind a shortage-only report
whose one piece of advice (add capacity) does not actually fix anything.

Demonstrated — 2 one-seat tables, 3 guests, one hard rule `r0` (SAME_TABLE g0,g1),
chart `{g0:t1, g1:t2, g2:t1}`, `movement_limit=0`:

```python
result = solve_event(ev, mode="low_disruption", current=current, movement_limit=0,
                      time_limit_s=10.0, seed=0, num_search_workers=1)
# status: infeasible
# report: conflict_rule_ids=(), capacity_shortfall=1,
#         recommendations=(add_capacity, add_table)   <- no rule, no limit named
```

Guards:
```python
# the real-limit probe this short-circuit SHOULD have used is exactly INFEASIBLE
_probe_status(_build_model(ev, eligible, current=current, movement_limit=0,
                            slack_bound=1)[0], 10) == cp_model.INFEASIBLE   # True

# every way to place the one extra seat, real limit held, r0 kept: still infeasible
for combo in [("t1",), ("t2",)]:
    grown = <tables bumped by combo>
    solve_event(grown, mode="low_disruption", current=current, movement_limit=0, ...).status
# both: "infeasible"  <- the report's own recommended fix does not restore feasibility

# dropping r0 AND adding the seat together does fix it
solve_event(<r0 dropped, t1 capacity 2>, mode="low_disruption", current=current,
            movement_limit=0, ...).status
# "feasible"
```

This directly violates ac2 ("removing all named rules ... and removing the seat limit
if a shortfall is counted makes the event solvable in the same mode"): nothing besides
capacity is named, and capacity alone never restores feasibility here. A fuzz pass of
250 random small low-disruption/planning events (checked by rebuilding each reported
fix exhaustively, same `combinations_with_replacement`-over-tables technique the hidden
ac3 property test already uses) found 19 more instances, all matching this same shape:
low-disruption, a real shortfall, a tight real movement limit, and a report naming only
capacity whose fix never actually cures the event.

None of this bean's own fixtures exercise this: every official/hidden test that combines
a low-disruption shortfall>0 with a rule uses a generous `movement_limit=100`, where
relaxing it further to "none at all" never differs from the real value — exactly the gap
this bug hides in.

## Defect 2: the caller's `time_limit_s` is silently ignored for the whole diagnosis

Every prior round (confirmed directly against the run-5 backup branch,
`origin/backup/bean-033-run5-20261014T113644Z`) threaded the caller's own `time_limit_s`
into every diagnosis probe, including the keep-set helper. This round introduces
`_PROBE_SECONDS: Final[float] = 2.0` (`hard.py:810-812`) and uses it in place of
`time_limit_s` at every call site inside `_multi_cause_search`, the shortage probes, and
the limit-lift probe — `time_limit_s` is accepted by `_diagnose_infeasibility` and
`_diagnose_low_disruption` (needed to match the `diagnose` callback type) and then never
read again in either function body.

Demonstrated — the hidden ac9 fixture (150 guests, 30 tables of 5, 6 packed locks, one
real contradictory pair), run at three requested time limits:

```python
for tl in (0.2, 0.05, 0.02):
    t0 = time.time()
    solve_event(ev, mode="planning", time_limit_s=tl, seed=0, num_search_workers=1)
    print(tl, time.time() - t0)
# 0.2  -> 21.61s
# 0.05 -> 21.92s
# 0.02 -> 22.11s
```

Requesting a 20-millisecond solve returns in ~22 seconds — a >1000x overrun — and the
wall time is identical across all three requests, proving `time_limit_s` has no effect
on the diagnosis path at all. Hand-patching `_multi_cause_search` and both shortage/limit
probes to use the real `time_limit_s` instead of `_PROBE_SECONDS` (tested in isolation)
restores the expected scaling (21.6s / 13.6s / 7.2s for the same three requests) while
all 10 hidden tests still pass — so this decoupling was not needed to fix ac9, and the
PR's own visible test for ac9 cannot catch it: it imports `_PROBE_SECONDS` directly and
asserts the production result against calls to the same constant, so it can only ever
confirm internal self-consistency, never that the budget tracks the caller's request.
This is the `spec.md` for this run's own gap: its `_multi_cause_search` signature
(`event, eligible, *, current, movement_limit, slack_bound`) never threads a time budget
through at all, leaving the implementer to invent one.
