## Context

Round 1 (reviewed `bean-017-20261019T142215Z.md`) found a demonstrated defect: `GuestImport.apply()` could crash with an uncaught `ValueError` when a later row's literal id collided with an earlier no-id row's auto-generated `imported-N` id, even on a preview-clean file. The bean gained ac6 for this. Round 2 is a full rewrite with a different, equally legitimate public API: free functions `preview_import(event, text)` / `apply_import(event, text, *, allow_partial=False)` operating on an in-memory `Event`, with a shared `_classify_rows` classifier.

## ac6 fix — verified correct

`apply_import` (`guest_import.py:308-335`) computes `reserved = {existing guest ids} | {every applyable row's explicit id}` once, before any row is applied, then `next_auto_id()` skips any `imported-N` in `reserved` and adds each newly minted id back into the set. I re-verified this independently with my own adversarial fixtures (not reused from the bean's or hidden test's code), run in the pinned gate image against the real PR tree:

- Multiple no-id rows interleaved with multiple literal `imported-N` rows (2 no-id + 2 literal, literal ids colliding with what naive sequential numbering would assign) → all 4 final ids distinct (`imported-3, imported-4, imported-1, imported-2`), no crash.
- A literal id colliding with an *existing* guest's id (classified `update`) followed by a no-id row → correctly updates in place and assigns a non-colliding `imported-2`, no interference.
- Every row carrying an explicit id (no auto-generation needed) → no crash, reservation set unused as expected.
- The bean's own two-row fixture, both orders → both apply cleanly with distinct ids, matching the bean's worked example exactly.
- `allow_partial=True` with an invalid row plus a within-file duplicate literal id (`dupid` claimed by two rows) plus a no-id row → the second `dupid` row is correctly classified `duplicate` and skipped on apply (consistent in both preview and apply, since both share `_classify_rows`), the no-id row gets `imported-1` with no collision.

All ac1–ac5 re-checked fresh (read-only preview, apply-matches-preview-counts, partial-import opt-in, deep-equal event on refusal) — no divergence found. Additional probes (CRLF, short/long rows, duplicate header columns, header case sensitivity, blank-vs-present `household_id` in the duplicate rule) all behave sensibly and consistently between preview and apply; no crashes, no preview/apply divergence.
