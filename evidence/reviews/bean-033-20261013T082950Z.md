# Pre-merge review: bean-033 run 1, run bean-033-20261013T082950Z

PR: beekeeper-lab/seating-planner-py#32 · reviewed 2026-10-13 by a fresh Claude session,
per `factory/review/PRE-MERGE-REVIEW.md`. bean-033's first run; no prior reviews.

**Verdict: do-not-merge.** Two defects demonstrated, both naming causes that are not
causes. The developer's own self-flagged soundness worry about the new "keep-set" probe
direction is confirmed in both directions it could fail.

## Baseline

99 tests pass on head against 97 on main; ruff, format and mypy are clean. ac1, ac2 and
ac3 pass as written.

## Defect 1: the keep-set probe lets one bad item implicate every partner

`hard.py:884` sweeps every pair of candidate items (`combinations(items, size)`)
without excluding a pair whose member already fails on its own. Since keeping a
larger combo is monotonically *more* constrained, a single item that is infeasible in
isolation makes every pair containing it infeasible too — so that one bad item drags
in every other rule and lock in the event as a named "cause."

- **Planning:** a 3-guest same-table rule (`r-big`) at a 2-seat table, plus an
  unrelated harmless rule (`r-ok`) and an unrelated lock (`g-5`). Head names all
  three; main names only `r-big`. Removing `r-big` alone restores feasibility —
  `r-ok` and `g-5` are in no conflict (brute-force confirmed).
- **Low-disruption:** a similar construction with a 0 movement limit (where any
  rule the current chart breaks fails alone) shows the identical pattern.

## Defect 2: with a plain seat shortage, every lock gets named

`hard.py:850-866`: when curing the shortfall alone (with everything else kept)
already restores feasibility, the search still probes removing locks one at a time.
Since nothing needed removing in the first place, removing any lock trivially
"succeeds" too, so every lock in the event is named as "part of the proven fix" —
when releasing it does nothing a seat couldn't have done instead.

Demonstrated: 2+2 seats, 5 guests, one lock, shortfall 1. Head recommends releasing
the lock; releasing it without adding a seat leaves the event infeasible, and adding
one seat with the lock kept already solves it. Main names no lock here. ac1's own
scenario 3 passes *because of* this defect — the lock it asserts gets named is not
part of any conflict under the bean's own "part of some conflict" definition.

## The keep-set soundness question, investigated directly

Both of the developer's own flagged risks are real:
- **Over-naming** (shown above): the "strictly additive, never worse" argument in
  impl-detail does not hold once an already-infeasible-alone item exists.
- **Under-fixing**: a constructed case with two contradictory rule pairs plus three
  guests locked to a 2-seat table has head name all 4 rules and no lock; removing
  them leaves the event still unsolvable. Main gives the generic note instead.
- ac2(a)'s own fixture needs 3 removals and passes *only* via the keep-set probe
  (turning it off fails ac2); that pass is particular to how the fixture is built,
  not evidence the probe is sound in general.

Random check, 900 generated small events with locks, rules and shortages, both
modes: head names a non-cause in 266 of 695 infeasible events (compared to 17 of
~700-ish on main); disabling the keep-set probe drops over-naming to 187 but then
47 named sets fail to actually restore feasibility (0 on head with it enabled, 149
on main, which mostly just gives up with the generic note instead of a wrong
answer).

## Performance

The keep-set probe has no early stop and checks every pair. 32 rules + 20 locks:
33.9s on head against 2.0s on main; even a plain shortage with no rule needed
(which should return immediately) takes 31.5s on head once locks are added to the
sweep.

## Minor

- The generic-note suppression (`suppress_generic_note=(not rules) or
  bool(named_locks)`, line 900) only hides the note when an unlock is actually
  shown; no case found where a needed note went missing.
- "Part of the proven fix" wording overclaims for every bystander named above.
- Affects both planning and low-disruption modes.

**Fix direction (not yet implemented or verified as a patch):** a combo named via
the keep-set probe must be a *minimal* infeasible keep-set — neither of a size-2
combo's size-1 members may themselves already be an infeasible keep-set, and an
item already proven infeasible alone is named for that reason and excluded from
larger combos. Separately, the lock-removal search in the shortage-only branch
must not run at all once curing the shortfall alone (with every rule and lock kept)
already restores feasibility — mirroring bean-032's ac5 treatment of harmless
rules, now needed for locks.
