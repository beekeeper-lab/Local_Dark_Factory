**VERDICT: do-not-merge.** Three defects, each demonstrated in the pinned gate image
against a `git archive` export of the branch.

1. **`unlocked` is accepted and ignored for a guest who also has an explicit lock.**
   `hard.py:381` skips only the day-lock pin; `_build_model` (`hard.py:442`) still calls
   `_apply_locks`, which pins every `event.locks` entry. Demonstrated with `locks={"g-2":"t-2"}`,
   `unlocked={"g-2"}` and a weight-100 soft rule pulling g-2 to t-1: the result is
   `{'g-0': 't-1', 'g-1': 't-1', 'g-2': 't-2'}`, g-2 does not move, and there is no error.
   This breaks ac4 and FR-067. The ac4 test uses empty `locks`.
2. **`elif mode is EVENT_DAY:`** (`hard.py:116`, `:186`) repeats bean-013's identity dispatch.
   With `"".join(["event", "_", "day"])`, a call with a chart raises "current does not apply to the
   planning mode". A call without one skips the chart requirement and runs a planning solve
   labelled `event_day`.
3. **An event-day solve with no seat available blames unrelated hard rules.** `_solve_event_day`
   passes `diagnose=_diagnose_infeasibility`, whose probe models leave out the day-lock pins.
   Demonstrated: `conflict_rule_ids=('r-unrelated', 'r-with-g0')`, with a recommendation to relax
   `r-unrelated`, which would not help. The spec declared this as an open limit.

Checked and sound: the pins are equality constraints, and nothing is bounded in only one
direction. Mutating the pin loop to `pass` fails ac1, ac2, ac3 and ac5 (4 failed, 1 passed),
so the tests do pin the behaviour.

Minor: an `unlocked` guest not on `current`, and a cancelled guest left on `current`, are
silently ignored. A chart entry that contradicts `event.locks` is infeasible with no
diagnosis naming the pin.
