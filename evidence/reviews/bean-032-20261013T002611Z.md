## Defect: "+shortfall at every table" admits far more than the shortfall, total

`hard.py:743` bounds each table's slack at the shortfall, but nothing bounds the SUM
across tables — with `n` tables, the model accepts up to `n × shortfall` extra seats
total, not one real placement of the shortfall. Two groups that each need a *different*
table to grow are both told capacity alone explains it, because each table separately
gets its own full allowance.

Tables of 2, 2 and 1 seats, 6 guests, a 3-guest same-table rule on each of two disjoint
groups, shortfall 1:

```
podman run --rm --network=none --userns=keep-id -v $S/head:/work:Z,ro \
  -v $S/demo3.py:/demo.py:Z,ro -e PYTHONPATH=/work/src -w /work \
  ghcr.io/beekeeper-lab/factory-gate-python:20260914 python /demo.py two_groups
head/main: infeasible, rules=(), shortfall=1, [add_capacity, add_table]
keep all rules, some real placement of 1 seat: None
keep all rules, +1 at EVERY table (head's model): feasible
drop A, some placement of 1 seat: {'t1': 3, 't2': 2, 't3': 1}
```

No single extra seat, placed anywhere, actually restores feasibility with both groups'
rules kept — yet the head's probe (and main's own shortage-only path) reports the
shortage alone as sufficient. Following that advice (add 1 seat) does not make the
event solvable. This breaks ac3 ("adding that many seats makes the event solvable"),
and the same gap exists on main — a shortage-only report with no rule conflict is never
checked against a real placement at all on either branch today. A second case with a
genuine rule conflict added (`two_groups_conflict`) shows the same gap.

**This is not a regression against main**; main is wrong here too, in the same way,
and the head is no worse — ac6's fix only changed the *rule-naming* path, and this gap
is in the *shortage-only* path that ac1/ac2/ac5/ac6 never touched. It is a genuine hole
in ac3's coverage that the bean's own acceptance criteria did not anticipate: ac6
requires "every table free to take up to the full shortfall", which — taken alone,
without also bounding the total used across tables — is a stronger model than "a real
placement of the shortfall exists", and that stronger model is what ac3 needs checked.

**Fix, tested:** keep each table's own slack bounded at the shortfall (so run 1's
unlimited-enlargement bug does not return), and add one further constraint inside
`build()`: the sum of actual overage used across every table is also capped at the
shortfall (11 lines, `fix.diff`). With it, both new cases are diagnosed correctly by
property check (every accepted "shortage alone cures it" claim is confirmed by finding
a real placement; every claim that a rule is needed is confirmed too), all 8 earlier
adversarial cases are unchanged, 96 tests still pass, mypy is clean, the three hidden
tests pass, and there is no measurable performance cost.
