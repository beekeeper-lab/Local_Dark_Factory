## Defect: the movement limit is held fixed in every probe, so it can hide a real cause

`hard.py:748-755` falls through from the ac7 leading probe into `_diagnose(...,
movement_limit=movement_limit, ...)`, and `hard.py:874-882`'s `make_model` always
passes that same fixed `movement_limit` to every removal and keep-set probe. The
limit itself is never one of the searchable items (`hard.py:849-851`). When the
frozen chart together with the limit is already infeasible on its own — independent
of any rule or lock — two things follow: every removal probe still fails (nothing
removable fixes a wall the probe never relaxes), and the empty-keep-set check
(`hard.py:923`, ac6's own gate) skips the whole keep-set search. The result: nothing
is named at all, even a rule contradiction that has nothing to do with capacity.

```
# 6 guests, three 2-seat tables, chart puts 3 guests on t1, movement_limit=0,
# a genuine same/different contradiction (r-a, r-b) on two OTHER guests
main: rules=('r-a','r-b')   recs=[change_hard_rule r-a, change_hard_rule r-b]
head: rules=()              recs=[('change_hard_rule', None)]   <- generic note only
guard: drop r-a, limit 99 -> feasible

# this run's OWN ac6 test fixture (test_named_causes_are_real_and_enough, part b)
main: rules=('r-1','r-2') shortfall=1 ...
head: rules=()            shortfall=1  recs=[add_capacity, add_table]
guard: +1 seat anywhere, limit 99, r-1 and r-2 both kept -> infeasible (x3 placements)
guard: r-1 dropped, same conditions                      -> feasible (x3 placements)
```
`tests/solver/test_complete_diagnosis.py:708` asserts `conflict_rule_ids == ()` for
that second fixture, locking in the empty report as "correct" — it isn't; r-1 really
is a cause, confirmed by the guard above.

A 1,000-event fuzz check (both modes) found 32 low-disruption events where main named
a real, brute-force-confirmed cause and head named nothing at all; all 47 of head's
"named set doesn't cure it" failures are reports that name nothing.

**Capacity and a raised limit, both genuinely needed:** neither tree handles this
today (0 cases found where either names the limit alongside a shortfall), so ac7's
own "whether or not the movement limit is also named" clause is currently
unreachable for this root cause — a known gap, not new, but worth fixing alongside
the above since the two share a root cause (the limit never being a searchable item).

**Fix direction (sketch, not yet a verified patch):** add the movement limit as one
more item in `_diagnose`'s combined search (alongside rules and locks) — "removing"
it means building that probe's model with `movement_limit=None` instead of the
fixed value. This lets the removal search find combos like {limit, rule} when both
are genuinely needed, and lets the empty-keep-set check (ac6) pass more often (since
relaxing the limit often cures a frozen-chart violation on its own), which in turn
lets the keep-set search actually run and find the independent rule cause. This also
closes the capacity-and-limit-together gap. Two existing test assertions (the one
quoted above, and possibly others depending on how scenario (a)/(b) are built) will
need correcting to match, the same pattern as runs 1-3.
