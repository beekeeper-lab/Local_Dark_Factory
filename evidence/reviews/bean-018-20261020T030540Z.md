I built adversarial `Rule`/rule-like fixtures and ran them in the pinned gate image:

- A rule whose membership is via `group_ids` only (the guest is in the group, not `guest_ids` directly) → correctly excluded. This matches the bean's literal spec ("whose `guest_ids` contains the guest"); it is under-inclusion, not a leak, so not a defect.

**Validation-before-output.** `_validate()` (unknown `include_private` name, then `_validate_assignments`) runs first in both entry points, before any row, warning, or audit write; confirmed by code path (single call site before any `csv.writer`/`audit.append`) and by the bean's own `test_unknown_private_field_raises` / `test_bad_assignment_target_raises`, both passing in the gate image.

**Audit.** Exactly one `audit.append()` call site, gated on `if include_private:` — structurally one entry regardless of field count, never one-per-field. `export_table_by_table_csv` takes no `AuditLog` parameter and only ever emits `table.name`/`guest.id`/`guest.name` pulled from `event`, never values taken verbatim from the caller-supplied `seatings` mapping — so a crafted `seatings` cannot smuggle extra data through it; validated by reading the only two `writer.writerow` call sites.

**ac5 edge cases.** A `seatings` entry naming a guest id absent from `event.guests` produces no row (the row loop is driven by `event.guests`, not by `seatings` keys) — confirmed. Two guests at the same table both appear; an unseated guest appears in none; an empty table contributes none — confirmed by the bean's own `test_table_by_table_export_complete`, which already includes exactly this mix. Ordering is table-order-then-guest-order, as specified, confirmed by code and test.

**Fresh adversarial probes (own construction, run in the pinned gate image):**
- CSV special characters (comma, embedded quote, newline) in a guest name round-trip correctly through the stdlib `csv` module — no corruption.
- `household_id=None` vs `household_id=""` both render as `""` — correct per the `guest.household_id or ""` pattern.
- **Minor, non-blocking:** if a future `notes` field is ever typed `str | None` and left `None` (not just absent), `_extract_notes`'s `str(getattr(guest, "notes", ""))` stringifies the explicit `None` to the literal text `"None"` in the private notes column, rather than `""` — because `getattr`'s default only applies when the attribute is missing, not when it's present and `None`. Unlike `locks`/`household_id`, there's no `or ""` guard. Reproduced: a `NotedGuest` subclass with `notes: object = None` produces a `notes` cell of `'None'`. No current field exists on `Guest` to trigger this, so it is forward risk only, already flagged in the bean's own "Open questions" as a different but adjacent mild trap — not a demonstrated defect in current behavior.
- **Minor, non-blocking:** `export_table_by_table_csv` assumes `event.tables`/`event.guests` carry unique ids (enforced by `Event.__post_init__`/`add_table`/`add_guest` on every real construction/load path, including `Repository.load_event`). If that invariant were ever bypassed by appending directly to `event.tables`/`event.guests` instead of going through the validated API, the double loop (table-outer, guest-inner, matching on `seatings.get(guest.id) == table.id`) would emit a duplicate row per guest for each table sharing the colliding id. Reproduced with two `Table` objects built with `id="dup"` and appended directly. This is not reachable through any sanctioned construction path in this repo today (every real caller uses `Event(...)` or `add_table`/`add_guest`, which both validate uniqueness), so it is reported as a hardening note, not a demonstrated defect of this bean.
