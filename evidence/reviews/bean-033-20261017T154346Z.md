## ac10 and ac11 are each correctly built for their own test's case

The shortage-only short-circuit that used to sit at the top of `_diagnose_low_disruption`
(and used the relaxed limit — run 6's bug) is gone; it is now inside `_pooled_cause_search`
(`hard.py:906-907`, `if shortfall > 0 and probe(frozenset(), frozenset())`), and `probe`
builds its model at the pass's own `movement_limit` (`hard.py:854-903`), which for pass 1
is the caller's real value. ac10's own fixture (2 one-seat tables, 3 guests, a same-table
rule forced apart by a frozen chart, `movement_limit=0`) now names `r0` alongside
`add_capacity`, and I confirmed independently that adding the one extra seat to either
table, real limit held, stays infeasible, while dropping `r0` and adding the seat together
cures it — matching the test and the bean's own background fixture exactly.

ac11's `_PROBE_SECONDS` constant is gone; every probe site in `_pooled_cause_search`,
`_probe_satisfiable`/`_probe_keep_set`, and the top-of-function limit probe takes
`time_limit_s` from the caller. Measured on the ac9/ac11 fixture (150 guests, 30 tables of
5, 6 packed locks, one real contradictory pair), planning mode:

```
time_limit_s=0.2   -> 2.74s   (conflict: ra, rb)
time_limit_s=0.05  -> 19.96s  (conflict: ra, rb)
time_limit_s=0.02  -> 9.19s   (conflict: ra, rb)
```

Non-monotonic, but never close to the ~22s-regardless-of-budget signature of run 6's bug,
and the hidden ac11 test's own threshold (elapsed < 15.0s at 0.02s) passed stably across 3
repeated runs (12.0-12.1s total for both timing tests together). The non-monotonicity is a
real side effect of threading the budget through — a smaller per-probe budget means more
probes return `UNKNOWN` instead of deciding, which can prevent the keep-set sweep's
early-stop condition (every item decided) from firing, so the sweep runs more combos, not
fewer. This did not surface a minimality or exactness regression in testing (see next
section) but is worth watching if the hidden test's 15s margin is ever tightened.

## Defect: pass 2's own shortage short-circuit silently drops the movement-limit cause

`hard.py:751-764`: `lifted` is set to `bool(named_rules or named_locks)` — true only when
pass 2's *removal or keep-set search* finds a rule or lock. But pass 2 (`movement_limit=None`)
runs the exact same `_pooled_cause_search` as pass 1, which starts with its own
shortage-only short-circuit (`hard.py:906-907`) at *pass 2's* movement limit — i.e.
unlimited. When a plain capacity shortfall is curable only once the real movement limit is
relaxed (no rule or lock involved at all), pass 1's shortage check fails (frozen guests
can't be reshuffled to absorb the shortfall where capacity is actually short), pass 1's
removal/keep-set search finds nothing (there is no rule or lock to remove — the cause is
purely the limit), pass 2 runs, and pass 2's *own* shortage check now succeeds (unlimited
movement lets the reshuffle happen) and returns `(frozenset(), frozenset())` immediately,
*before* `lifted` is ever set. The caller sees "pass 2 named nothing" and reports a plain
`add_capacity`/`add_table` — the one case `raise_movement_limit` needed to be named, and
isn't.

Reproduced — 3 tables of capacity 2 (6 real seats), 7 guests, no rules, no locks,
`movement_limit=0`, chart `{g0,g1,g2,g3: t1, g4,g5: t2, g6: t3}` (t1 overfull by 2, global
shortfall 1):

```python
result = solve_event(ev, mode="low_disruption", current=chart, movement_limit=0,
                      time_limit_s=10.0, seed=0, num_search_workers=1)
# conflict_rule_ids: ()
# capacity_shortfall: 1
# recommendations: add_capacity, add_table   <- no raise_movement_limit
```

Guards:
```python
# the real-limit-held fix the report itself recommends (add 1 seat, any table) never works:
for tid in ("t1", "t2", "t3"):
    grown = <tables, +1 capacity at tid>
    solve_event(grown, mode="low_disruption", current=chart, movement_limit=0, ...).status
# all three: "infeasible"

# raising the limit alone (no capacity change) also fails -- it's a genuine shortfall too
solve_event(ev, mode="low_disruption", current=chart, movement_limit=99, ...).status
# "infeasible"

# only limit AND capacity together cure it
solve_event(<+1 seat at t1>, mode="low_disruption", current=chart, movement_limit=99, ...).status
# "feasible"
```

This directly violates ac2 ("removing the seat limit if a shortfall is counted makes the
event solvable in the same mode"): the shortfall is counted, capacity alone does not
restore feasibility, and `raise_movement_limit` — the one recommendation that would have
told the caller the truth — is missing. It is the same defect shape run 6 introduced and
ac10 was written to close (a shortage-only short-circuit silently probing a question
easier than "does the real limit permit this"), reappearing because this round folded that
short-circuit into the pass-shared `_pooled_cause_search` without teaching the pass-2
caller that *its own* shortage shortcut, not just its removal/keep-set search, can be the
reason pass 2 "found nothing."

A fuzz pass of 220 small random low-disruption/planning events (2-3 tables, capacity 1-2,
0-3 rules, 0-2 locks, random charts and movement limits 0/1/2/100) found 5 more instances
of exactly this shape among 197 infeasible results — all low-disruption, all
`conflict_rule_ids=()`, no unlock, `capacity_shortfall > 0`, `raise_movement_limit` absent,
and the reported capacity fix confirmed (via the same guard above, every placement of the
shortfall's seats at the real limit) to not restore feasibility. 0 false positives among
the other 192 (every other named report's fix, checked the same way, does cure the event).
This is a systemic gap in the new architecture, not a one-off construction.

None of this round's own tests catch it: `test_a_rule_is_still_named_when_only_relaxing_the_limit_would_cure_the_shortage`
always has a rule in the mix, so pass 1's removal search finds it and pass 2 never runs.
No test in this round or any prior one exercises a plain shortfall, zero rules, zero locks,
where only the limit needs lifting under the new pooled-search structure.

## Minor

- `_pooled_cause_search`'s keep-set phase (`hard.py:986-1074`) now carries a
  `phase_budget = time_limit_s * len(pool) * len(pool)` wall-clock guard on top of each
  individual probe's own `time_limit_s` bound — a real, new attempt at the open
  "pair sweep has no early stop" complaint every prior review raised. It did not fire in
  any of my timing or fuzz runs, so I can't yet say whether it under- or over-bounds the
  sweep in practice; worth watching in a future round if large events still run long.
- The non-monotonic timing in the ac11 measurement (0.05s slower than both 0.2s and
  0.02s) traces to more probes going `UNKNOWN` at a tighter budget, which can suppress the
  keep-set sweep's "everything already decided" early stop. No minimality or
  INFEASIBLE-exactness failure observed from it in this review's fuzzing, but it means the
  diagnosis's total wall time is not a simple function of `time_limit_s` — only bounded by
  it in aggregate via `phase_budget`, not proportional to it.
